# v0.1.49 benchmark results

The full native amd64 resource study completed **217 trials with 434 fresh
Gateway pods**. Each selected slot setting passed **3/3 resource-stable,
HTTP-clean trials**; an adjacent setting was tested three times with an
observed OOM. These are workload-specific resource edges with very little
memory headroom, not recommended production settings.

[Open the interactive HTML report](../assets/benchmarks/v0.1.49-amd64.html)
for size selection and memory, latency and occupancy charts.

Raw development artifacts have been removed from the current source tree.
Evidence links below use the immutable pre-cleanup Git revision; the interactive
report above remains part of the public documentation.

## Runtime and method

- Runtime: released **v0.1.49**, source
  [`48c93c07d42b113b8073a403604b111871bf0fda`](https://github.com/sarattha/relayna-gateway/commit/48c93c07d42b113b8073a403604b111871bf0fda).
- Image: `ghcr.io/sarattha/relayna-gateway@sha256:1b40a38f8c5f211d9c5b650a450c4645ee53149d1af7235599afdc133ea69f75`.
  This historical image index contains amd64; it is not an arm64 release image.
- Two pods per trial; **each** capped at **2 CPUs / 1 GiB memory**, with a
  **512 MiB serialized-body budget**. CPU and memory values below are per pod.
- Native amd64 Ubuntu hosts with four shared vCPUs and approximately 16 GB RAM;
  fixtures share that host. Per-size CPU models, precise Docker resources,
  measurement timestamps and image/node provenance are retained in the raw
  environments. Cross-size timing includes differences between hosts.
- Exact 5/10/20/40/80/100 MiB JSON with one string field, HTTP/1.1 keepalive,
  direct equal traffic to each pod, no TLS, compression or retries. Streaming
  mock verifies length/hash and upstream credential handling without retaining
  complete bodies. Real PostgreSQL/Redis provide authentication/control state.
- Upstream pauses reads for 10 seconds, then delays the response for two seconds
  after upload. Absolute client deadline is 60 seconds. Resource stability is
  the criterion; latency has no SLO. Final comparisons use **1024 simultaneous
  requests per pod**, or **2048 offered requests per trial**. Earlier discovery
  cohorts remain separate in the raw evidence.
- Results independently validated on **2026-10-22 UTC**. The released runtime
  was measured by separately versioned benchmark harnesses; exact per-size
  harness commits and source snapshots are linked below.

## Resource edges

RSS/cgroup values are the highest individual-pod observations across the three
selected stable trials. Headroom is 1024 MiB minus the cgroup peak. Adjacent
failed-trial memory may be censored by process death; it is not substituted for
the stable setting's memory. All selected stable trials had no restart/OOM.

| JSON | Stable slots/pod (3/3) | Adjacent slots: OOM trials | Peak RSS / cgroup (MiB) | Headroom (MiB) |
| --- | ---: | --- | ---: | ---: |
| 5 MiB | 128 | 129: 1/3 | 888.5 / 1005.71 | 18.29 |
| 10 MiB | 215 | 216: 2/3 | 830.9 / 947.54 | 76.46 |
| 20 MiB | 127 | 128: 1/3 | 882.5 / 1022.34 | 1.66 |
| 40 MiB | 177 | 178: 2/3 | 836.4 / 993.30 | 30.70 |
| 80 MiB | 174 | 175: 2/3 | 831.6 / 1010.82 | 13.18 |
| 100 MiB | 130 | 131: 1/3 | 822.3 / 1023.75 | 0.25 |

The 100 MiB setting left only **0.25 MiB** observed cgroup headroom. Increasing
slots to these edges in production would leave little protection against
workload variation. The byte budget counts retained serialized bytes; JSON
analysis, connection state, allocation capacity and other pod memory also
contribute to the 1 GiB ceiling. Slot ceilings are not preallocated memory.

## Timing and request outcomes

Each latency value is the **worst per-trial percentile** among the three
selected stable trials, in seconds. These columns are not one pooled
latency distribution. Elapsed is the longest complete batch duration. Counts
are across **both pods in a single trial**, shown as ranges over three trials;
every trial offered 2048 requests. Successful bodies were independently
verified. Most offered requests were intentionally denied by admission.

| JSON | Success p50 / p95 / p99 (s) | Rejection p95 (s) | Elapsed (s) | Verified 200s/trial | HTTP 503s/trial | Transport errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 5 MiB | 35.46 / 36.58 / 38.37 | 26.56 | 39.11 | 206 | 1842 | 0 |
| 10 MiB | 28.74 / 30.95 / 30.98 | 19.48 | 31.30 | 104 | 1944 | 0 |
| 20 MiB | 35.21 / 40.18 / 40.25 | 28.09 | 40.73 | 50–51 | 1997–1998 | 0 |
| 40 MiB | 36.61 / 40.15 / 40.23 | 29.47 | 40.74 | 24–26 | 2022–2024 | 0 |
| 80 MiB | 48.03 / 59.93 / 59.93 | 41.02 | 59.96 | 12–16 | 2032–2036 | 0 |
| 100 MiB | 33.95 / 37.12 / 37.12 | 26.26 | 37.59 | 10 | 2038 | 0 |

All **18 selected stable trials** were HTTP-clean, with zero lost denial
replies, other HTTP statuses, restarts or OOMs, and admission gauges returned
to zero. Failed exploration trials remain in the evidence. Resource-stable
exploration trials with exactly counter-accounted lost denial replies retain
those client errors separately; they were not relabeled HTTP-clean.

## Reproduction and provenance

This initial baseline predates the portable CLI. Original Actions jobs used
`mode=full` with one `body_mib` per job and the pinned runtime digest above.
The run links and archived harness source preserve their original settings.

To measure the same released runtime with today's CLI on a **native amd64**
host, record a separate rerun directory:

```sh
scripts/bench-body-admission run \
  --image ghcr.io/sarattha/relayna-gateway@sha256:1b40a38f8c5f211d9c5b650a450c4645ee53149d1af7235599afdc133ea69f75 \
  --body-mib 5 10 20 40 80 100 --repetitions 3 \
  --output target/release-benchmarks/v0.1.49-rerun
```

This command is a current reproduction recipe; the tables retain the original
historical measurements. Future versions use the
[current release protocol](index.md#required-protocol), with native source
builds available on either supported architecture.

## Comparison and scope

This is the first entry under the mandatory per-version policy. The older
[5 MiB baseline/improved experiment](https://github.com/sarattha/relayna-gateway/blob/8903a62191d461f12c53d10108b1c880452945eb/internal/test-reports/body-admission-5mib/amd64/README.md)
used a different fixed-rate protocol and is not a like-for-like predecessor for
this six-size resource search. No speedup/regression percentage is inferred.

The newer [native ARM CLI smoke tests](https://github.com/sarattha/relayna-gateway/blob/8903a62191d461f12c53d10108b1c880452945eb/internal/test-reports/body-admission-cli/README.md)
validate the portable tooling with source-built images, one slot and two offered
requests per pod. They do not establish six-size ARM resource edges or replace
the v0.1.49 native amd64 baseline.
