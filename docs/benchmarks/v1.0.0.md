# v1.0.0 release benchmark

The native ARM64 study completed **179 trials with 358 fresh Gateway pods**.
All six selected settings have three resource-stable confirmations. The 5 and
10 MiB settings are conservative tested lower bounds; 20–100 MiB have three
adjacent OOM confirmations. These finite resource observations leave little
memory headroom and are **not production defaults**.

!!! note "Evidence scope and release checks"
    Resource, matched-latency and ten-minute local measurements passed independent
    validation. Final-head GitHub CI passed both ten-minute checks, and the owner
    merged PR #143 before tagging. The [v1.0.0 release](https://github.com/sarattha/relayna-gateway/releases/tag/v1.0.0)
    is published with all 60 prepared evidence and screenshot assets; downloaded

## Runtime and method

- Runtime and harness: committed
  [`766bf17ee1e1f9da409870fdc40a48b691bfa81c`](https://github.com/sarattha/relayna-gateway/commit/766bf17ee1e1f9da409870fdc40a48b691bfa81c),
  clean at measurement. Subsequent CI/test/docs changes preserve the production
  build inputs. Source workspace version is 1.0.0; the benchmark image's optional
  version label was unavailable and is recorded as `unknown`.
- Immutable ARM64 image:
  `sha256:1c9ee503bed1772698380d6424bd8ceb1afffbf86b6927efc9af0a6d50e96b91`.
- Measured **2026-10-24 22:27:51 to 2026-10-25 01:02:33 UTC** on native
  Apple M1 Pro / arm64. Docker Desktop 29.8.2: 10 CPUs and 20,940,111,872 bytes
  of memory (19.50 GiB); kind node v1.36.1 / arm64. Host, Docker, Gateway image
  and node architectures match; no emulation was used.
- Two fresh Gateway pods per trial, each **2 CPUs / 1 GiB memory / 512 MiB
  serialized-body budget**. PostgreSQL, Redis and the streaming mock share the
  Docker host. No competing builds, tests or external load ran during measurement.
- Exact **5, 10, 20, 40, 80 and 100 MiB JSON**, direct equal HTTP/1.1 traffic to
  each pod, no TLS, compression or retries. The streaming mock verifies admitted
  length, SHA-256 and credential translation without retaining whole bodies.
- Adaptive simultaneous bursts use 512 requests/pod during initial discovery,
  then larger cohorts when required. Selected 5 MiB confirmations offer
  **1,024 requests/pod**; selected 10–100 MiB confirmations offer **2,048/pod**.
  Raw rows retain each trial's actual cohort. Upstream pauses reads for ten
  seconds, then delays its response for two seconds after upload.
- Every size uses one fixed **180-second absolute client observation window**,
  a 300-second condition-runner deadline and a 600-second outer trial deadline
  including setup/evidence. Resource stability is the criterion, not a latency SLO.

```sh
scripts/bench-body-admission --json doctor
scripts/bench-body-admission --json run --build \
  --body-mib 5 10 20 40 80 100 --repetitions 3 \
  --output target/release-benchmarks/v1.0.0-r3
```

## Repeated resource observations

RSS and cgroup values are the highest individual-pod observations across the
three selected stable trials. Headroom is 1,024 MiB minus the observed cgroup
peak. Selected stable trials have zero OOM/restarts. Failed-trial memory can be
censored by process death and must not replace the stable setting's evidence.

| JSON (MiB) | Slots/pod (3/3 stable) | Offered/pod | Interpretation | Adjacent slots: OOM trials | Peak RSS / cgroup (MiB) | Headroom (MiB) |
| --- | ---: | ---: | --- | --- | ---: | ---: |
| 5 | 99 | 1024 | tested lower bound | 100: 2/3 | 715.81 / 1005.86 | 18.14 |
| 10 | 43 | 2048 | tested lower bound | 44: 1/3 | 769.56 / 1009.16 | 14.84 |
| 20 | 24 | 2048 | confirmed resource edge | 25: 3/3 | 824.71 / 1013.45 | 10.55 |
| 40 | 11 | 2048 | confirmed resource edge | 12: 3/3 | 797.06 / 1003.33 | 20.67 |
| 80 | 5 | 2048 | confirmed resource edge | 6: 3/3 | 761.46 / 971.60 | 52.40 |
| 100 | 4 | 2048 | confirmed resource edge | 5: 3/3 | 773.90 / 973.81 | 50.19 |

The automated discovery report had only one successful 5 MiB trial at 112 slots.
The independent audit instead selects the repeated 99-slot setting. Its adjacent
100-slot setting OOMed in two of three trials; the 10 MiB adjacent setting OOMed
in one of three. Both are reported as lower bounds rather than repeated edges.
All original discovery rows and reports remain in the raw archive.

The serialized-byte budget does not cover JSON analysis, allocations, connection
state or other process memory. Admission slot ceilings do not preallocate memory.
Use deployment-specific headroom; do not deploy these near-OOM settings as defaults.

Across **all exploration and confirmation trials**, there were 31,514 verified
HTTP 200s, 170,247 admission HTTP 503s and 210,591 transport errors. Of 179 trials,

and censored memory remain attached to failed trials. No other HTTP status was
observed. The owned benchmark cluster was removed after evidence collection.

## Matched observer latency

The observer comparison uses the **same authentication offloading in both arms**.
Its measurement-only control disables new observer collection/publication while
retaining released Traffic journaling, durable accounting, policy, authentication
and body admission. It is not the unpatched v0.1.49 runtime and is never a release
image. The exact four-file patch and client harness are retained with checksums.

- Control image:
  `sha256:26cc01d4662d63eba195943a491c641ae0363816774e8d0aff7547fd976e8ae6`.
- Control patch SHA-256:
  `ed1792e1320000121a4eddb9f2096c8f00e7256518cd07a7baf30d4767cd357b`.
- Same native host and pod caps; eight body slots/pod; **1 MiB JSON at 12 requests
  per second total**, no upstream delay, 30-second warmup, legacy Prometheus
  scrapes every 250 ms and no interactive viewers.
- Two 15-second pilots, then six 180-second formal trials in balanced order:
  control/enabled/enabled/control/control/enabled. Each trial starts fresh pods
  and dependencies. All eight owned clusters were removed.
- Each arm has **6,480 verified HTTP 200s**, with zero errors, OOMs or restarts.
  Percentiles below are independently recomputed from all successful raw requests,
  without averaging pod or trial percentiles.

| Arm | Success p50 (ms) | p95 (ms) | p99 (ms) |
| --- | ---: | ---: | ---: |
| Matched control | 68.322 | 75.341 | 95.835 |
| Observer enabled | 68.655 | 74.563 | 84.950 |

Enabled/control ratios are **0.98967 at p95** and **0.88642 at p99**, satisfying
the predeclared ≤1.05 gate for this workload. This finite comparison is not a
general speedup or production-capacity claim. Per-trial variability, dispatch lag,
memory observations, dependencies and pilot results remain in the raw evidence.

## Continuous monitoring check

The required `monitoring smoke` CI job observes HTTP, SSE and WebSocket traffic
for **600 continuous seconds**, excluding build/setup/cleanup. It uses two fresh
native Gateway processes, a disposable database with 100,000 synthetic events,
30 projects/20 shared services, and concurrent all-project Usage reads. Quiet
socket probes, an explicit socket renewal, observer lease renewals, terminal
outcomes, privacy, bounded registries/body capacity, drain and slot recovery are
asserted. The local CI-equivalent run completed **600.001 seconds** on 25 October
2026: each instance served **2,394 successful HTTP requests**, 149 complete SSE
streams and 49 intentional interruptions. Both socket replacements and all 19
observer lease renewals per instance passed, with no unexpected errors, observer
gaps or missing fleet coverage. Active/body gauges drained to zero and both socket
slots recovered per instance. Fixture cleanup passed. Concurrent all-project Usage
reads succeeded. The newly added GitHub CI job must pass on the final PR head.
[Run instructions](https://github.com/sarattha/relayna-gateway/blob/main/tests/e2e/monitoring/README.md)
explain evidence and limits.

A **24-hour soak is optional and manual**, requiring an intentional operator run.
It does not gate CI, PRs or releases. No 24-hour result is claimed. Short checks,
including earlier six-minute runs, do not prove long-term stability.

## Retained failures and interpretation

Earlier attempts and diagnostics are preserved separately, without substituting
them for the final all-six-size study:

1. The first burst study and unchanged native ARM64 v0.1.49 reproduction exposed
   `store_unavailable` responses. Database wait samples were mostly idle. Isolated
   bounded Argon2 offloading removed those errors at the identical cohort; the
   production fix preserves cryptography, key-state checks and cancellation bounds.
2. The earlier 60-second study completed 45 trials at 5 MiB and 19 at 10 MiB before
   unfinished 4,096-request bursts were censored. A declared 180-second diagnostic
   drained a 32-slot 10 MiB trial in 77.4 seconds: 441 verified successes, zero
   OOM/restarts and 16 lost denial replies reconciled by counters. Its 1,024-slot
   trial still OOMed both pods. It motivated a consistent observation window;
   diagnostic rows are not mixed into the final repeated results.

[The v0.1.49 baseline](v0.1.49.md) used different native **amd64** hardware,
cohorts and observation deadlines. Slot or timing changes are not like-for-like
performance regressions or improvements; no cross-architecture speedup is inferred.
